# Развёртывание TruckProfit

## Что уже есть

Репозиторий содержит миграции PostgreSQL, Telegram webhook и web-кабинет Next.js. Секреты задаются в окружении сервера, не в Git и не в клиентском JavaScript.

## Нужны от владельца проекта

1. URL проекта, publishable key и service role key — только в secret store развертывания.
2. Перевыпущенный Telegram bot token перед production-запуском. Токен не добавляется в Git, n8n или клиентский JavaScript.
3. Решение, кто будет первым `OWNER`, и 2–3 тестовых водителя для пилота.

## Новая среда

1. В новом Supabase-проекте выполнить **все** файлы `supabase/migrations/*.sql` в порядке номера (в текущем наборе — `00001`–`00041`). Четырёх первоначальных миграций для текущего приложения недостаточно. Demo seed не запускать в рабочей базе.
2. Проверить, что bucket `expense-receipts` остался private. Водитель не получает service role key и не ходит в БД напрямую.
3. Настроить URL конфигурации Auth: development URL и redirect URL `<домен>/auth/confirm`.
4. Задать серверные переменные из `.env.example`, выполнить проверки ниже и развернуть Next.js. Для закрытой беты выдать приглашение владельцу через административный интерфейс; затем зарегистрировать его через `/register` и создать компанию через `/onboarding`.
5. Добавить машины, водителей и активный рейс через web-кабинет.
6. Добавлять водителей и сотрудников через кабинет, передавать им персональные приглашения. Не создавать подключения ручным изменением Telegram ID в базе.
7. Настроить Telegram webhook на `https://<домен>/api/telegram` с `secret_token`, совпадающим с серверной переменной `TELEGRAM_WEBHOOK_SECRET`. При работающем webhook не запускать long polling того же бота. Токен не вставлять в команды, которые попадут в историю или журнал.

## Обновление существующей среды: исправления от 07.09.2026

Сначала проверить, что в среде уже применены миграции до `00038` включительно. Не повторять весь набор поверх существующей базы: часть миграций намеренно не идемпотентна. Перед изменением схемы использовать штатный резервный снимок/backup базы и проверить возможность восстановления.

Применить новые миграции в следующем порядке:

1. `00039_operational_integrity.sql` — защита soft-delete и назначение водителя после внесения планового дохода.
2. `00040_telegram_reliable_processing.sql` — аренда обработки Telegram update, защита повторных операций и атомарное сохранение состояния диалога.
3. `00041_report_delivery.sql` — ограничение частоты отправки отчёта в личный Telegram.

Для SQL Editor можно выполнить эти три файла одним запросом, обернув их содержимое в `begin;` / `commit;`. Если часть уже применена, сначала сверить объекты и историю миграций, а не выполнять повторно. Исправления файлов `00034` и `00035` нужны для воспроизводимости **новой** базы, в существующей их повторять не требуется.

**Только после успешного обновления базы публиковать новый код:** новый обработчик Telegram использует функции из `00040`. Обратный порядок временно остановит обработку сообщений. Новые секреты для этого выпуска не требуются; отправка файлов использует существующий `TELEGRAM_BOT_TOKEN`.

После публикации проверить на отдельных тестовых данных:

- редактирование без права удаления, изоляцию двух компаний;
- назначение водителя рейсу с плановым доходом, уведомление и «Мой рейс»;
- расход и чек в Telegram, смену статуса и геометку;
- CSV/PDF с фильтрами в браузере и отправку файла из Mini App;
- связь профиля пользователя с его личным Telegram перед отправкой финансового отчёта.

Нельзя считать локальные тесты подтверждением работы production. Статус выпуска фиксируется отдельно от результатов проверки кода.

## Проверки перед выпуском

```sh
npm ci
npm run lint
npm test
npm run typecheck
npm run build
npm run test:ui
```

`npm test` включает PostgreSQL-тесты в изолированном PGlite: они применяют весь набор миграций, не обращаются к production и не используют рабочие credentials. Отдельный запуск — `npm run test:db`.

`npm run test:ui` проверяет реальный компонент выгрузки и CSS в Chrome при ширине 390 и 1366 px, но использует тестовые ответы API. Требуется установленный Google Chrome. Это не заменяет проверку на физическом устройстве с Telegram.

## Telegram-гарантии

- персональное приглашение привязывает Telegram к заранее созданному водителю, сотруднику или владельцу;
- `telegram_update_logs` и аренда диалога не дают одновременно обрабатывать один update/чат разным серверным экземплярам; `FAILED` и истёкшая аренда допускают повтор;
- успешный HTTP-ответ webhook отправляется после обработки; состояние диалога и `PROCESSED` сохраняются одной транзакцией;
- результат записи расхода, статуса, одометра, геометки или старта/окончания плеча сохраняется с ключом update+операция, чтобы повтор не создавал вторую запись;
- запись расхода, одометра и статуса проходит через серверные SQL-функции, которые проверяют организацию, водителя и активный рейс;
- чек загружается в private Supabase Storage и сохраняется отдельным attachment;
- Telegram показывает водителю только его рейс и его предварительную зарплату, не внутреннюю прибыль компании.

Повторная доставка зависит от Telegram; долговременная очередь входящих payload пока не реализована. Отправка сообщений и загрузка файлов во внешнее хранилище не являются частью транзакции PostgreSQL: при сетевом сбое возможен повтор уведомления или вложения, хотя повторная финансовая запись защищена.

## Роль n8n

n8n подключается после запуска ядра как интеграционный слой: напоминания о ТО, уведомления о задержке, подтверждённый импорт из Sheets и отправка ежедневной сводки. Он не хранит диалоги бота, P&L или права доступа.

## Критерий первого пилота

Один собственник создаёт машину и многоплечевой рейс; водитель привязывает Telegram по invitation, добавляет топливо/чек, пробег и статус; менеджер вносит доход; dashboard показывает согласованный P&L, себестоимость/км, прибыль/км и порожний пробег.
